1. Visión General del Problema

El sistema actual opera como una instancia independiente por establecimiento: cada petshop tiene su propia base de datos Supabase, su propio catálogo de productos y sus propios clientes registrados. Esto es correcto para la operación interna, pero genera un problema cuando se quiere ofrecer una experiencia unificada al cliente final a través de una app móvil.

El objetivo es permitir que un cliente busque, por ejemplo, "Royal Canin" y obtenga resultados de todos los establecimientos que utilizan el sistema, ordenados según su historial de compras, cercanía y precio — sin que los stores tengan que cambiar nada en su operación.

2. Arquitectura General

La solución se basa en un Hub Central: un servicio independiente que actúa como agregador de información. Los stores empujan datos al hub mediante webhooks; la app móvil solo habla con el hub. Los stores individuales no se modifican en su lógica de negocio.

3. Pieza 1 — El Hub Central

Un proyecto Supabase nuevo, completamente independiente de las bases de datos de los establecimientos. Su única responsabilidad es consolidar información para servir a la app móvil.

Tabla: stores

El directorio de todos los establecimientos registrados.

CREATE TABLE stores ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), nombre TEXT NOT NULL, direccion TEXT, ciudad TEXT, lat DECIMAL(10,7), -- latitud para cálculo de distancia lng DECIMAL(10,7), -- longitud para cálculo de distancia api_url TEXT NOT NULL, -- URL del Supabase de esta tienda activo BOOLEAN DEFAULT true, created_at TIMESTAMPTZ DEFAULT now() ); -- Datos de ejemplo: -- id | nombre | ciudad | lat | lng | activo -- tienda-A | PetShop Ñuñoa | Santiago | -33.4569 | -70.5987 | true -- tienda-B | Animal Planet | Vitacura | -33.3901 | -70.5734 | true -- tienda-C | Pelitos Felices | Maipú | -33.5123 | -70.7456 | true

Tabla: catalog_index

Copia desnormalizada del inventario de todas las tiendas. Un mismo producto puede aparecer N veces — una por cada tienda que lo vende, con su precio y stock propios.

CREATE TABLE catalog_index ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), store_id UUID REFERENCES stores(id), producto_nombre TEXT NOT NULL, marca TEXT, precio INTEGER, -- precio en pesos CLP stock_disponible INTEGER DEFAULT 0, imagen_url TEXT, ultima_sync TIMESTAMPTZ, -- cuándo se actualizó por última vez searchable TSVECTOR -- columna para Full Text Search ); -- Índice para búsqueda full-text CREATE INDEX idx_catalog_fts ON catalog_index USING gin(searchable); -- Datos de ejemplo: -- store_id | producto_nombre | marca | precio | stock | ultima_sync -- tienda-A | Royal Canin Adult | Royal Canin | 25000 | 12 | 2026-03-30 14:00 -- tienda-B | Royal Canin Adult | Royal Canin | 23500 | 8 | 2026-03-30 13:45 -- tienda-A | Purina Pro Plan | Purina | 19000 | 5 | 2026-03-30 14:00 -- tienda-C | Purina Pro Plan | Purina | 18000 | 20 | 2026-03-30 12:30
¿Por qué Royal Canin aparece dos veces? Porque es un registro por tienda. No existe un catálogo "maestro" — cada tienda nombra sus productos como quiere. El hub guarda copias independientes de cada store. Esto es intencional: permite precios distintos, stocks distintos y nombres ligeramente distintos por establecimiento.

Tabla: customers

Identidad global del cliente. Un RUT = un registro, independientemente de cuántas tiendas haya visitado.

CREATE TABLE customers ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), rut TEXT UNIQUE NOT NULL, -- identificador universal nombre TEXT, email TEXT, telefono TEXT, created_at TIMESTAMPTZ DEFAULT now() ); -- id | rut | nombre | email -- c-1 | 12.345-6 | Juan | juan@gmail.com -- c-2 | 67.890-1 | María | maria@gmail.com -- c-3 | 98.765-4 | Pedro | pedro@gmail.com

Tabla: customer_store_history

Relación muchos-a-muchos entre clientes y tiendas. Es la clave para el ranking personalizado: saber cuánto y cuándo compró cada cliente en cada establecimiento.

CREATE TABLE customer_store_history ( customer_id UUID REFERENCES customers(id), store_id UUID REFERENCES stores(id), total_compras INTEGER DEFAULT 0, monto_historico BIGINT DEFAULT 0, -- en pesos CLP ultima_compra DATE, PRIMARY KEY (customer_id, store_id) -- un registro por par cliente-tienda ); -- customer_id | store_id | total_compras | monto_historico | ultima_compra -- c-1 | tienda-A | 5 | 125.000 | 2026-03-28 -- c-1 | tienda-B | 2 | 48.500 | 2026-03-10 -- c-2 | tienda-A | 8 | 210.000 | 2026-03-30 -- c-3 | tienda-B | 1 | 23.500 | 2026-02-25 -- c-3 | tienda-C | 3 | 87.000 | 2026-03-20 -- Juan (c-1) ha comprado en A y B → aparece 2 veces en esta tabla -- Pedro (c-3) ha comprado en B y C → aparece 2 veces

4. Pieza 2 — Sincronización de cada Store al Hub

Cada establecimiento necesita un mecanismo para notificar al hub cuando algo cambia: un precio, el stock de un producto, una venta nueva, o un cliente nuevo.

Opción A — Webhook en tiempo real (recomendada)

Supabase permite configurar Database Webhooks que ejecutan una Edge Function automáticamente cuando una fila cambia. La Edge Function envía los datos al hub.

// Edge Function en el Supabase de cada tienda // Archivo: supabase/functions/sync-to-hub/index.ts // Se dispara automáticamente con trigger ON INSERT/UPDATE en tabla "productos" Deno.serve(async (req) => { const payload = await req.json(); // datos del row que cambió const { record } = payload; await fetch(`${Deno.env.get("HUB_URL")}/api/sync/catalog`, { method: "POST", headers: { "Content-Type": "application/json", "Authorization": `Bearer ${Deno.env.get("HUB_SYNC_SECRET")}`, }, body: JSON.stringify({ store_id: Deno.env.get("STORE_ID"), productos: [{ nombre: record.nombre, marca: record.marca, precio: record.precio, stock: record.stock, }] }), }); return new Response("ok"); });

Opción B — Cron periódico (más simple para comenzar)

Un job programado (cada 15 minutos, por ejemplo) que lee el inventario completo del store y lo envía al hub. Acepta un pequeño retraso en la información mostrada en la app.

// Cron en la app web de cada tienda (Next.js route handler) // GET /api/hub-sync → llamado por Vercel Cron o GitHub Actions export async function GET() { const supabase = createServiceClient(); const { data: productos } = await supabase .from("productos") .select("nombre, marca, precio, stock") .eq("activo", true); await fetch(`${process.env.HUB_URL}/api/sync/catalog`, { method: "POST", headers: { "Authorization": `Bearer ${process.env.HUB_SYNC_SECRET}` }, body: JSON.stringify({ store_id: process.env.STORE_ID, productos }), }); return Response.json({ ok: true }); }

Sincronización de ventas (para historial de clientes)

Cuando se registra una venta en el store, también se notifica al hub para actualizar el historial del cliente. Esto alimenta el ranking personalizado de la app.

5. ¿Cómo Nace un Cliente en el Hub?

Esta es la pregunta central. Los clientes "nacen" en los stores individuales, pero el hub los unifica por RUT. Hay dos caminos posibles, y pueden ocurrir en cualquier orden:

Camino A — El cliente descarga la app móvil primero

1
Cliente abre la app e ingresa su RUT La app envía el RUT al hub para verificación.
2
Hub busca si el RUT ya existe en la tabla customers Si no existe, lo crea con los datos básicos que ingresó.
3
Hub consulta en background a cada tienda registrada Pregunta: "¿tienen un cliente con RUT 12.345-6?" usando la api_url de cada store.
4
Consolida las respuestas Tienda A: "Sí, Juan, 5 compras" → Tienda B: "Sí, Juan, 2 compras" → Tienda C: "No"
5
Guarda el historial en customer_store_history El cliente ya puede ver sus tiendas favoritas en la app.

Camino B — El cliente compra en una tienda antes de bajar la app

1
Pedro compra en Tienda C El vendedor lo registra normalmente en la app web de la tienda.
2
La venta dispara el webhook de sincronización POST hub/api/sync/purchase con { rut: "98.765-4", store_id: "tienda-C", monto: 23500 }
3
Hub verifica: ¿existe RUT 98.765-4? No existe → crea el registro en customers. Sí existe → solo actualiza el historial.
4
Cuando Pedro descarga la app e ingresa su RUT Ya tiene su historial precargado. La app lo reconoce inmediatamente.
Conclusión clave sobre clientes Un RUT = un registro en el hub, siempre. No importa si el cliente existe en 1, 2 o 10 tiendas distintas. El hub es la fuente única de verdad de la identidad del cliente. Las tiendas individuales mantienen sus propios registros locales sin modificar nada.

Flujo de búsqueda de producto

Juan escribe "Royal Canin" + activa GPS │ ▼ App → GET hub/api/search?q=Royal+Canin&lat=-33.45&lng=-70.60 Hub ejecuta en catalog_index: SELECT ci.*, s.nombre, s.lat, s.lng, s.direccion FROM catalog_index ci JOIN stores s ON s.id = ci.store_id WHERE ci.searchable @@ plainto_tsquery('Royal Canin') AND ci.stock_disponible > 0 │ ▼ Resultado sin ordenar: ┌───────────────────────────────────────────────────────┐ │ Royal Canin Adult │ Tienda A (3.2km) │ $25.000 │ 12u │ │ Royal Canin Adult │ Tienda B (8.5km) │ $23.500 │ 8u │ └───────────────────────────────────────────────────────┘ │ ▼ Hub consulta historial de Juan: → tienda-A: 5 compras ← comprador frecuente → tienda-B: 2 compras ← ha comprado antes → tienda-C: 0 compras │ ▼ Aplica ranking y devuelve al app: #1 Royal Canin Adult | PetShop Ñuñoa (Tienda A) Compraste aquí 5 veces | 3.2 km | $25.000 #2 Royal Canin Adult | Animal Planet (Tienda B) Compraste aquí 2 veces | 8.5 km | $23.500

Lógica de Ranking

#1
Fidelidad — Historial de compras Primero aparecen las tiendas donde el cliente ha comprado más veces. Si hay empate, se pasa al siguiente criterio.
#2
Cercanía — Distancia GPS Entre tiendas con igual historial, se prefieren las más cercanas. Solo aplica si la diferencia es mayor a 1 km.
#3
Precio — Menor precio primero Como criterio de desempate final. Favorece al cliente económicamente.
// Implementación del ranking (TypeScript) function rankStores( results: StoreResult[], history: Record<string, { total_compras: number }>, userLocation: { lat: number; lng: number } ) { return results.sort((a, b) => { // 1. Fidelidad const aFid = history[a.store_id]?.total_compras ?? 0; const bFid = history[b.store_id]?.total_compras ?? 0; if (aFid !== bFid) return bFid - aFid; // 2. Distancia GPS (fórmula haversine) const aDist = haversine(userLocation, { lat: a.lat, lng: a.lng }); const bDist = haversine(userLocation, { lat: b.lat, lng: b.lng }); if (Math.abs(aDist - bDist) > 1) return aDist - bDist; // 3. Precio return a.precio - b.precio; }); }

7. ¿Cómo se Incorpora un Nuevo Establecimiento?

El proceso está diseñado para ser lo más simple posible. El nuevo dueño no necesita saber nada sobre el hub — solo configurar 3 variables de entorno.

1
El dueño se registra en el panel de administración del hub Ingresa nombre del establecimiento, dirección y datos de contacto.
2
El hub genera credenciales únicas Un STORE_ID (UUID) y un HUB_SYNC_SECRET (token seguro para autenticar el sync).
3
El dueño configura 3 variables en su instancia de la app STORE_ID=xxx | HUB_SYNC_SECRET=xxx | HUB_URL=https://hub.tudominio.com
4
Se activa el webhook de sincronización El catálogo de la nueva tienda comienza a aparecer en el hub en minutos.
5
La tienda es visible en la app móvil Sin cambios en el código del store. Sin modificaciones a la base de datos. Solo 3 variables de entorno.
Lo que NO cambia en la app actual de cada tienda La aplicación web de gestión interna queda exactamente igual. El vendedor sigue usando el POS, registrando ventas, gestionando inventario exactamente como antes. El único cambio es la adición del webhook de sync al hub — y esto se puede configurar como una opción que se activa/desactiva desde el panel de settings.

8. Stack Tecnológico Recomendado

Hub — Base de datos Supabase (nuevo proyecto) Mismo stack que los stores individuales. Familiar, escalable, con FTS nativo.
Hub — API Next.js (App Router) o Hono Mismo framework que la app actual. Endpoints /search, /sync, /stores, /me.
Sincronización Supabase Database Webhooks + Edge Functions Nativo en Supabase, sin infraestructura adicional. Alternativa: cron.
App Móvil React Native + Expo Un solo codebase para iOS y Android. Ecosistema maduro.
Autenticación cliente JWT firmado por el hub (RUT como claim) Sin contraseña. El RUT es el identificador universal.
Búsqueda de productos Supabase Full Text Search → Algolia si escala FTS nativo aguanta hasta ~500 tiendas sin infraestructura extra.
Geolocalización expo-location + fórmula Haversine Sin APIs de pago. Cálculo de distancia en el servidor con lat/lng.
Notificaciones push Expo Push Notifications Para alertas de stock (alimento por agotarse), integrable con consumo_alertas.

9. ¿Qué pasa si una Tienda se Cae o Desconecta?

EscenarioImpacto en el HubImpacto en la App Móvil
Tienda sin internet por 1 hora catalog_index muestra el último snapshot conocido El producto aparece con badge "info actualizada hace Xh"
Tienda cambia precio sin sync Precio desactualizado hasta próxima sincronización Precio puede diferir al llegar al local (aceptable)
Hub cae temporalmente — App móvil no funciona. Stores internos siguen operando normalmente.
Tienda se da de baja Se marca como activo=false en stores Desaparece de búsquedas automáticamente
El hub no es crítico para la operación interna de los stores Si el hub cae, el POS de cada tienda sigue funcionando con normalidad. Solo se ve afectada la app móvil de los clientes finales.

10. Escalabilidad — ¿Cuándo Migrar?

EscenarioSolución actual (FTS Supabase)Cuándo migrar
1 – 50 tiendas FTS nativo de Supabase No es necesario migrar nada
50 – 500 tiendas FTS + índices bien configurados Monitorear tiempos de respuesta
500+ tiendas Migrar catalog_index a Algolia o Typesense El resto de la arquitectura no cambia
Miles de usuarios móviles simultáneos Escalar el hub en Vercel/Railway Solo el hub, los stores no se tocan
La arquitectura está diseñada para escalar incrementalmente Cada pieza puede ser reemplazada o mejorada de forma independiente. Agregar una tienda nueva nunca requiere modificar el código del hub ni de otras tiendas.
